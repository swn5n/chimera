# Chimera

Personal app: "SheepIt for agents." Split the task, not the model. Each step runs whole on one node with a model (or a Head/tool) that fits. General-purpose, not Blender-specific (Blender is just one thing to test with).

Current version: **0.8.0** (Nov 1, 2026: worker routing, repairs, the scene check and the look; 0.7.0 was Oct 29, Hydra 1.0, released Oct 30 with the Head maker merged in; 0.6.1 was Oct 25, 0.6.0 Oct 24). All computers on the pool must run 0.6.1 or newer: from 0.6.1 the computer running a Head reads its options, and the hub honours `not_here`. A 0.6.0 worker runs such Heads on their defaults, and the hub says so in the reply. Update the hub host and the Head computers first. Only put `hydra:1.0` on computers running 0.7.0 or newer: older builds (and an older hub) treat it as an ordinary chat model. Not enforced in code: `hubProto` (app/hub.go) is still 1, so a 0.5 device can still join. To bump the version, change `const Version` in app/main.go (build.sh fills in Info.plist) plus the README.md title.

To join a test instance to the real pool as an asker only, set `auto_help` off or it lends itself. A second instance on the same `--ui-port` quits with "already running", so check which process holds the port (`lsof -iTCP:<port> -sTCP:LISTEN`) and kill by that PID: a `./chimera` command line doesn't match a pattern on its folder.

## Ports
- 7470 local UI (127.0.0.1; falls back to 7471-7474, `--ui-port`)
- 7480 hub (host only, all interfaces, `--hub-port`)
- 7479 UDP discovery (needs SO_BROADCAST; on macOS also the Local Network permission)
- Ollama at 127.0.0.1:11434 (`$OLLAMA_HOST` / `--ollama`)
- Devices only dial out. Heartbeat 3 s; long-poll `/v1/work`.

## Decided (from the user; don't relitigate)
- Lending is a manual Connected / Disconnected toggle (like SheepIt), no idle detection. Light use of the computer is fine while connected.
- Disconnecting mid-job offers "finish current step, then disconnect" and "stop now".
- Ollama must be running before a device can connect.
- General-purpose, not Blender-specific.
- Dark grey design using the chimera icon and logos.
- Download models from inside Chimera, picked to fit each device with headroom. Work out each device's context limits, model limits and installed tools.
- If nobody is lending, a chat runs on the user's own best model.
- Show what each device is best for and which waiting work it could help with.
- Long tasks get a system prompt telling each node it is one small piece of a larger project; the prompt varies by task type.
- Internal library of known-working mechanics, reused instead of calling models ("distilling ourselves"). 5-star rating after replies; 4-5 stars asks what worked; the network's largest GPU turns that into a central library entry. When spare compute is idle for a set time, test library entries for spam or mistakes; errors flag for the host.
- Web app, installable so it shows in the macOS Dock with the Chimera icon.
- Testing credits: everyone gets 1,000,000 starter credits; set back to 100 after testing. Going negative must actually limit you.
- Devices on the same Wi-Fi connect automatically (no code/IP sharing). A user's own devices auto-connect to help with their long tasks.
- Looping mode = iterate until done: parse (planner), sub-agents (workers), piece (combine), review, repeat.
- Open pool: anyone on any network can auto-join and contribute; credits (not codes) prevent freeloading. **Privacy is explicitly NOT a goal for now** ("ideally privacy is something we can do but for now lets just get it working"). Don't add encryption or privacy work unprompted.
- Tools are called **Heads** in the UI/docs (code, `plugin.json` and API keep `plugin`). A user's custom tool (e.g. the Perspective Blender plugin for studio shadows) should be called instead of an AI model when it does the job better. Rate Heads with the 5 stars. A Head owner whose tool gets called earns extra credits for bridging AI with deterministic techniques. Keep it open for future tools. Integrate other local AI models (mainly 3D mesh and picture generation) from the Nvidia PC.
- Heads run off the computer that hosts them and just return results to the asker via the chat. The asker's own computer (its GPU) is used for Head work only when the Head is its own (installed there). Applies to all future Heads.

## Architecture notes
- Routing: `need_caps` / `need_ctx` / `prefer`; context buckets 8K/32K/64K/128K; local fallback with a note. Stalled/offline steps retried elsewhere (3 tries). Worker steps (Oct 31, `hub_workers.go`) use `prefer: "worker"` with the task's id: the hub learns the seconds a step takes per computer and model (`worker_secs` in `hub.json`, only from worker steps) and picks the lowest cost, not the biggest model. Cost = those seconds, or a guess from speed plus `workerUnproven` 600 for an untimed model; load time if not loaded; `workerSmallCost` 1000 under 8B; 45 s per step that computer already did for the task, up to 2 (`workerSpreadMax`). An empty or cut-off reply is learned as 300 s worse. A free computer at least 45 s better that isn't polling gets up to `helperWait` (`workerAboutToAskLocked`). Chats, the combine and a one-step plan's only step keep the old scoring (`workerPrefer`). A free slow computer still takes a step ahead of a busy fast one, on purpose so far (`docs/joint-task-oct31.md`, Routing). `pickLocalModel` uses the same guess.
- Long tasks (Hydra, `hydra.go`): the helper model (else the biggest model) plans 2-7 JSON steps, parallel workers (max 4) with per-kind prompts, verified library entries reused, biggest model combines. Only in looping mode ("Keep going until done", off by default) does it then review (`{done, score, critique}`, the helper else the biggest model) and re-plan, up to 6 passes (`hydraMaxRounds`). `score` is unused, and a non-integer score fails the parse and ends the loop as if done. A later round that errors keeps the best result so far (`keepRound`, with a note) instead of failing the task.
- Repairs, later rounds and the best round (Oct 31, `hydra_mend.go`, `execute` in `hydra.go`; why: `docs/joint-task-oct31.md`). A script that fails the check gets up to `hydraMends` (8) repairs inside its round (`mendScript`, phase `mending`): the biggest model gets only the script and the error (`hydraMendPrompt`) and replies with FIND/REPLACE edits (`editFormat`); `applyEdits` puts them in the script, `withScript` puts the script back in its code block by position (`pickBlock`), and it's checked again. Two tries in a row that get nowhere end it (worse, which is taken back, `Undone`; nothing that applies; the same error on the same line). `applyEdits` matches without trailing spaces, then without indents (`reindented`), since wrong indents were most misses. An edit matching several places changes them all unless it only adds lines (`keepsAll`). `parseEdits` drops an edit that adds a code fence, one that ran into the next, and repeats. A reply that writes the script out counts if it's about as long with mostly the same lines (`writtenOut`). From round 2 workers get the result so far and the critique (`earlierForWorker`, `earlierLimit` 40,000 characters; the planner's 12,000 and its text are unchanged), and so does the combine; for a script, unless the last result was cut off, the combine replies with edits (`synthEditPrompt`), a one-step plan still goes through it, and its reply isn't streamed. A round whose edits change nothing (`Unchanged`) isn't reviewed and doesn't count as better. `roundResult` holds each round's text and the record behind it; `grade` ranks a script with nothing known wrong (passed, unsure, skipped) over one that runs part-way, one that doesn't start, no script, cut off, and an empty round last. Ties go to the later round. The next round works from the best round (`best.Critique`), two rounds in a row that don't improve stop the loop, and `keepBest` restores the kept round's plan and models and sets `Kept` and a note, also on Stop (`stop` in `execute`). A script that stopped on an error the check couldn't judge gets a note on the reply, and the error joins the next critique (`unsureLine`).
- The real names (Oct 31, `blenderCrashNames` in `runner.go`, `crashNames`/`takeNames` in `hydra_check.go`). As Blender dies on a wrong name, a `sys.excepthook` from the check's prelude looks at the real object and prints one line, `namesMarker` plus JSON: attributes (closest first, and `on`, the pointer that holds the name, like `image_settings` for `file_format`), collection keys, `bpy.ops` and `bmesh.ops` keywords, and the real operators of that family. Only Blender 5.2's Python sets `e.obj` on every error, so it works from the failing statement's header. Deny by default, so a run means the same with it (`TestTheNamesHookLeavesTheVerdictAlone`): `ours()` refuses anything the script defined, `read()` reads only module attributes, built-in RNA properties and plain non-heap objects (a script can register getters on Blender's own types), builtins are bound in the prelude, gc and tracing are off while it runs, warnings are filtered, and a name is only given if the object matches the error and really lacks it. Output is capped at about 1,500 bytes, and `takeNames` strips the line before `lastPyError` reads the output. The list goes at the end of `crashCritique`, and through `unsureLine`, as data; `hydraMendPrompt` says to use only those names. It's for honest mistakes: a script aimed at the hook could slip past it, and the sandbox is what holds a script in. A missing operator counts as the script's fault (`noOperator`) if Blender has that family of operators (`opSpace`) and neither the goal nor the script mentions an add-on (`addonRe`). With names and up to 9 repairs 18 of 21 real crashed scripts passed, against 11 of 21 without, in half the tokens (`docs/joint-task-oct31.md`); at 5 repairs the gain doesn't show, hence `hydraMends` 8. `finalCheck` (Go and app.js) follows `Kept` and skips undone repairs. `run.kinds` keeps every plan's kinds, so a later plan labelled otherwise can't hide a script. The combine's budget cuts only over 60,000 characters in all, longest first (`pieceCap`).
- Result check (Oct 29, `hydra_check.go`; facts before opinions): in looping mode, before the review, the asker runs the round's Blender or Python script (`pickScript`: a closed ```python block of 6+ code lines; Blender if it imports bpy and a plan/step kind is blender, code or general; plain Python only for code plans; list-item indents and whole-script indents are removed) in the sandbox (`runSandboxed`, runner.go: Blender `-b --factory-startup --python-exit-code 1`, a `--python-expr` prelude that stops at the first render, 120 s; Python `-I`, 30 s). `judgeRun` is deliberately conservative (a goal that says `-b` or headless can't blame Blender's missing window, `headlessRe`, `uiContextRe`): "failed" only for a definite crash in the script (SyntaxError, IndentationError, TabError, NameError, UnboundLocalError, AttributeError, TypeError; for Blender also RuntimeError/ValueError/KeyError/ImportError, and an IndexError on Blender's own collections in something the script made, `indexesWhatItMade`), after `envReason` lets through anything that may come from the computer, the sandbox, a fresh scene, inputs or another Blender version, and `otherBlocks` excuses a NameError for a name another block of the result mentions (or an AttributeError for a property another block sets up); `envReason` also excuses the person's selection or mode (`selectionRe`, unless the script sets it up first), add-ons, another computer's GPU backend or OS calls, command-line arguments, file access anywhere in a multi-line statement, and a Blender version the goal names that differs in major or minor; and a traceback only counts when it ended the run (`pyError.Last`, not a handled one). Everything else is passed, unsure or skipped and the reviewer decides as before. A failed check, after its repairs (or a combine cut off at its output limit: `done_reason` "length", carried by `genEvent.DoneReason`), skips that round's review and becomes the next planner's critique (data, through the existing "What still needs work" text: no prompt changes); the same fault twice stops the loop. After a cut-off the next combine (or a one-step plan's step) gets more room (`cutRoom`: NeedCtx plus `num_predict` up to 16,384). Only on the computer that started the task, never through the hub; setting `check_results` ("Run my long tasks' scripts here to check them", default on once); needs macOS's sandbox or bwrap on Linux (`checkSandboxOK`, `profile.can_check`), never Windows; no `riskyScript` pre-filter (library runs keep it). The task record has `checks` (per round and repair: `mend`, `undone`) and `cut_steps`; the card shows them; `finalCheck` (the delivered result's) sets the saved reply's note. The macOS script profile (shared with library runs): no network, home and volumes unreadable, writes only in the run folder, `(deny process-exec*)` except the tool (and a `#!` launcher's interpreter and the .app it starts), `(deny process-fork)`, signals only to itself, no Apple Events, LaunchServices or pasteboard. A `/bin/sh` watchdog outside the sandbox kills the script (by pid, so `setsid` can't escape) and the run's process group when the app dies or the check is stopped (verified with kill -9 and with a setsid script). A Blender found through a launcher script (Homebrew's) is resolved to the app binary it starts (`launcherTarget`, tools.go), since the sandbox can't fork. `chimera --check-result <reply.md|script.py> [--check-goal …]` runs the same check from a terminal.
- The scene check (Oct 31, `blenderSceneFacts` in `runner.go`, `hydra_scene.go`; why and numbers: `docs/joint-task-oct31.md`). After a Blender script finishes (`blenderMeasureScene`, a second `--python-expr`) or as its render starts (`_chimera_stop_at_render`), the prelude measures the scene and prints `sceneMarker` plus JSON; `judgeRun` turns certain faults into outcome `wrong_scene` (`withScene`, `sceneFaults`), which goes to repairs, then the next round, without a review, like a crash; the note on a saved reply says what's wrong. It claims little on purpose, because a false alarm costs repairs that can damage a good scene: objects whose boxes are provably outside the frame when the goal says to frame everything (`wholeGoalRe`) and the camera isn't among them (`among`), a camera that reaches nothing at all, no camera when the goal clearly wants one (`cameraGoalRe`, `noCameraRe`, `aimedGoalRe`), meshes with no vertices, and the original factory cube (by `session_uid`, untouched) in a task that builds a scene (`newSceneRe`). Rays never prove something is missing, unless nothing at all is reached: they miss what's small and stop at glass. Objects count only if they'd render as something to frame: helpers, curves without faces, and flat or glowing objects outside the frame don't. Tasks on the person's own file (`ownSceneRe`), add-ons, animation, handlers, several populated scenes, and goals not in English go unjudged. `grade` is a float: wrong scenes rank by faults left, then share in frame, above a script that stopped part-way (`Partway`). Told only the fault, repairs fixed 15 of 30 real scenes; given a view that was worked out and tried with rays (`_chimera_pose`: location and rotation_euler), 26 of 30. If measuring hangs or crashes after the start marker, the script still passed (`takeScene`). A script that saves to the top of the disk under `-b` counts as a crash (`rootFileRe`), since it would never reach the measuring. It can't tell shape, scale or light: an upside-down table passes. Everyday goals (Nov 1, `docs/joint-task-oct31.md`): a goal asking for a scene (`newSceneRe`, `sceneWords`) wants a camera unless it rules one out (`noCameraRe`), and that camera has to show what the goal names (`goalThings`: the last word of each noun phrase; `unshown`; off if the camera stands among the objects, with a second camera, for a tight goal (`tightGoalRe`) or one that says what the camera is for (`shotGoalRe`), unless nothing asked for shows at all, `noneNamedShown`). A place word carried only by an extra doesn't count once something else named shows (`isPlace`). To say something's missing the word must match (`sameWord`); to say it's shown it may start a longer word (`hasWord`). `cut` in the prelude: the frame could hold it, under half of its box is in, and under 46 rays reach it (12 for a rod). A plain mesh with a material and no faces counts as no geometry. There's deliberately no count of objects out of frame: it fired on 37 good pairs and 3 bad ones.
- The look (Nov 1, `hydra_look.go`, `renderLook` and `blenderLook` in `runner.go`, `ChatImage` in `ollama.go`). The last step of a check, only if the rest passed and `wantsLook` (a scene from nothing, not animated, no add-on, not a tight goal, no camera ruled out). The prelude saves the scene (`lookBlend`) at the end of measuring, packing textures painted in code, unless it's Workbench or there's no camera. A second Blender, same sandbox and watchdog, `--factory-startup --disable-autoexec`, renders it (512 px, 16 samples, CPU, 20 s limit), so the script's code doesn't run again. `lookPNG` is removed first and read only if it's a plain file under 5 MB, since a script had that folder first and this read is outside the sandbox. A vision model on this computer lists the objects asked for (`lookPrompt`, JSON by `lookFormat`, temperature 0, no thinking). `withLook`: `wrong_scene` if blank with nothing seen, or strictly more than half unseen; if a second camera or a named shot means this one may show only part (`partOfIt`), only seeing none of it counts. Any failure leaves the check as it was. Only `qwen3.8:` models judge (`lookModel`, `CHIMERA_LOOK_MODEL` to try another): gemma4:12b flagged more than twice as many good pictures. Never through the hub: `ChatMessage` has no images, so a worker on an older build would answer blind. `grade` puts a look's fault (`Look`) above a measured one. Stop during a look keeps the pass. On 40 held-out scenes it flagged 0 of 13 good and caught 15 of 27 bad, against 4 by the rules alone.
- Helper model (0.7.0; `helper.go`, `helper_share.go`): Hydra 1.0 (`hydra:1.0`, Qwen3-4B-Instruct-2507 + LoRA, Q5_K_M, 2.9 GB, `num_predict` 4096 in its Modelfile) does three jobs: Hydra's planner, the looping reviewer, the words-only Head gate. Those steps carry `prefer_model` (only when `need_ctx` <= `helperMaxCtx` 7000, i.e. the 8K bucket; the helper was trained on up to 8,192 tokens). Reviews have a lower limit, `helperMaxReviewCtx` 3500 (`helperForReview`, about 5,800 characters of result): on `eval-long` it missed most flaws in results of 8,300 characters and more (see Build and test). In `fits`, a device with that model scores `preferredScore` (1e6) minus `eta`, so it wins over everything; with none, `prefer` decides as before. A *free* helper device that isn't long-polling at that moment (it has just finished a step, typically the combine right before a review) gets up to `helperWait` (3 s, `helperFreeLocked`) before others may take the step, and a `time.AfterFunc` dispatch at the deadline hands it on; a busy one (all slots used) isn't waited for. Without this wait the review regularly went to a smaller model in `hydra_test.py`. Everywhere else `ModelInfo.ForChat()` keeps the helper out (`isHelperModel` matches any `hydra:` tag): ordinary scoring, `largestLocked`, local fallback (`pickLocalModel`), Head options (`fastestChatModel`), `bestFor`, help items, the chat picker (`forChat` in app.js); naming it explicitly still works. Unreadable plan or review from the helper: asked once more without `prefer_model` (`askPlanner`/`askReviewer`); note "largest" only chooses among devices waiting at that moment, so the retry can land on a smaller model if the biggest is still busy (unchanged dispatcher behaviour). Prompts are unchanged on purpose: the helper was trained on exactly `hydraPlannerPrompt`, `hydraReviewPrompt` and `headGatePrompt`; change them and it needs retraining. The task record has `reviewer_device/owner/model`; a one-step task's reply shows its worker's model, not the planner's.
- Getting the helper (`helper_share.go`): the host's App builds an offer from its own Ollama (`/api/show` modelfile `FROM` blob path, else the manifest in `$OLLAMA_MODELS` or `~/.ollama/models`, `manifests-v2/ollama.com/library/hydra/1.0` or the older `manifests/registry.ollama.ai/...`), cached and rebuilt in the background when the model's digest changes. The hub advertises it in `network.helper`, serves `GET /v1/helper` (digest, template, parameters parsed from `/api/show`, licence) and `GET /v1/helper/model` (1 MB writes, each with a `helperStall` (60 s) write deadline so a sleeping member frees its slot; 2 at a time, 429 beyond). A member's Models page "Get from host" calls `POST /api/helper/install` (SSE progress): HEAD `/api/blobs/<digest>`, else streams the file into `/api/blobs`, then `/api/create` with `files: {"hydra-1.0.gguf": digest}`. The upload's `countingReader` only counts (atomic): the transport reads it on its own goroutine, even after Ollama has answered, so progress comes from a ticker that's stopped before `installHelper` goes on; no progress for `helperStall` stops the copy. Nothing comes from the internet.
- Hosting: open pools run `mergeLoop` (sweep discovery every 20 s; step down and join an outranking open host). `staleHubWatch` rejoins or re-enters `autoPool` when the hub is unreachable; "neither joined nor hosting" is never a resting state. `autoPool` order: pool address, LAN discovery (joins only if exactly one open host answers), auto-host election. Known gap: after about a minute without its pool-address hub, a device auto-hosts and never retries the pool address (Hosting persists across relaunch).
- Updates: `takeOverOlder` makes a newer build quit an older running one via `/api/quit` (needs `X-Chimera: 1` header). On macOS, `handOverOnMac` (main.go) spawns a detached daemon (`CHIMERA_DAEMON=1`, Setsid) so a second double-click reaches `main` and opens the window. `CHIMERA_NO_DAEMON=1` disables; `--no-open` also skips the handover (tests use it; use it to keep Chimera in the foreground from a terminal). `CHIMERA_HANDOVER_TEST=1` is the Linux test hook.
- Heads: sandboxed worker, hub registry. A message with a picture always goes to a Head (`choosePlugin`), whatever model is picked. The hub's search (`/v1/plugins`, `pluginCandidatesLocked`) only counts Heads on devices the request may run on: `pluginScope` carries "Run on" (`target`) and "Only my devices" (`private`). Before Oct 25 it ranked the whole pool, so a better-rated Head elsewhere won and the pinned step failed ("FX3 can't run the … plugin"). Askers need this build to send the scope; an older asker still gets the old behaviour. Words-only messages with "Best available" go through `headForText` / `runWordsOrHead` with `headGatePrompt` (`{"use": bool}`, temp 0); an explicit model skips Heads for words-only messages. Manifest fields: `accepts`, `optional_input`, `network: "localhost"`. macOS sandbox-exec; Linux bubblewrap or user+mount+net namespace (localhost Head gets the whole network there). Where no sandbox exists (always on Windows; Linux without bwrap/unshare), Heads are refused unless the owner enables `unsandboxed_heads`. A Head's `--probe` runs unsandboxed everywhere; only step runs are sandboxed.
- Head work stays off the asker (0.6.1): the asker sends a `run_plugin` input with no `options` key. The computer running the Head fills them in (`withPluginOptions`, plugin_chat.go) with the model that answers soonest (`eta`). That's a *shared* model, or any model for its owner's own steps. It unloads that model afterwards if nothing was using it (`modelInUse` asks Ollama live; `ChatStreamKeep` with `keep_alive` "0s"), sends the "Options from your request" line back as a step `note` (cleared on requeue), and counts the time in the Head charge.
- The words-only gate is submitted with `not_here` unless the Head runs on the asker (`headRunsHere`: installed *and* its probe passes). With `not_here`, the hub excludes the asking device and `runPrompt` never falls back to local. If no other computer takes the gate within 8 s (`gateWaitElsewhere`), the word-match rule decides. An input that already has `options` (from an older build) is run as it is; a pre-0.6.1 worker gets a hub note instead (`optionsOnWorkerSince`).
- Head maker (`headmaker.go`, Settings → Heads → Make a Head): a form makes a Head with no code, of kind `program` (a command line, run without a shell, with `{{input}} {{prompt}} {{out}} {{name}} {{cache}} {{blender}} {{seed}}` and settings) or `server` (an HTTP call to 127.0.0.1 only, JSON template, `{{input_base64}}`/`{{input_data_url}}` or multipart upload, result found by itself or via `result_field`). The answers live in plugin.json's `maker` block; `headkit/run.py` reads them. Only Heads with a `maker` block can be changed in the form (`POST /api/heads` with `replace`, bumps the patch version). `POST /api/heads/{id}/try` runs any Head installed here once (re-probes, options read by a local model, the real sandbox) and streams SSE; files are kept in `head-tries/<id>/`. Tried for real on the Studio under sandbox-exec with `say`, Blender 5.2 (user add-ons load), `cp` and a fake local server; never yet against rembg, A1111 or a real Hunyuan3D server.
- **Known bug (macOS):** a `network: "localhost"` Head gets the whole network (internet, LAN). `(allow network* (local ip "localhost:*"))` in `macPluginSandboxProfile` (app/plugins.go) also matches outbound connects. Splitting it into `network-outbound (remote ip ...)` plus `network-bind network-inbound (local ip ...)` fixed it in direct sandbox-exec tests. `TestLocalhostNetworkSandbox` only string-matches, and `heads_text_test.py` prints "Internet: OPEN" without failing.
- Credits: 1 credit = 1,000 output tokens from a reference ~8B model; weight = total params/8 for larger (MoE models are charged by total, not active, params); prompt tokens count 10%; Head steps 2 credits/min of worker time (capped by the hub's own clock). Zero-sum between people; own devices free; library jobs free. Network mints: starter credits, Head run bonus `max(0.1, 50% of charge)`, Head star bonus 1.0 per 4-5 stars from someone else (`pluginBonusShare/pluginBonusMin/pluginStarBonus` in `hub_plugins.go`). Below 0 the hub refuses (402) any submission that could use others' devices; only "Only my devices" work goes through. The check runs at submit, so in-flight steps can push a balance lower; the -50 soft floor only moves your queued steps behind everyone else's.
- Library (`library.json`) and ledger (`hub.json`) live with the hosting computer; only the host (joined over loopback) is admin and runs scripts (opt-in, sandboxed). Chats are stored only on the sending computer, except rated replies: their prompt and response go to the host's `library.json` (`feedback`, last 500) for curation.
